# tstack on T3 Code

This guide shows how tstack maps onto T3 Code, and how to set T3 up and check on running work.
[runtime-t3.md](../../skills/tstack/references/runtime-t3.md) owns the exact calls the agents make.

## What runs where

| Role | In T3 | Checkout |
| --- | --- | --- |
| Lead | The thread you open for the task | Its own worktree, when you open the thread in **New worktree** mode |
| Worker | A child task of the lead, titled `<task id> <name>` | The lead's worktree |
| Coordinator | Only for an autopilot: the thread you open in **Current checkout** mode, with Full access, pinned | The project folder |

A worker that must build or run competing code, such as an arena candidate, gets its own thread and worktree instead.

## Start a task

Open one thread per task.
In the composer, switch from **Current checkout** to **New worktree**, and pick the project's default branch as the base branch.
T3 names the branch.
Then send `$tstack` with your goal and how you will know it is done.
The thread runs on whatever model you picked in the composer.

Your sidebar is your task list, one thread per task.

If you start a ship task in **Current checkout** instead, the lead moves it.
It starts a new thread titled `<task id> lead` in a worktree on `task/<task id>`, tells you to continue there, and stops.
Starting a thread needs **Full access**.
Without it, the lead asks you to open a New worktree thread and paste a launch block it gives you.
A read-only question can run in any checkout.

The lead that a move or a handoff starts runs on the `lead` seat in your models file.
The seat does not apply to the thread you open yourself.

## Set up T3 once

- Sign in to each provider your models file uses, under Settings, then Providers.
  Setup reads the providers T3 can run and refuses a model it does not list.
- Give a thread **Full access** when it may need to start another thread: a lead that might move its task, and every coordinator.
- Optional: under Settings, then Integrations, turn on browser access, and device access for a mobile app.
  Leads and workers then drive your app in T3's browser or simulator, and save screenshots and recordings as evidence.
  This surface has not yet run in a live task.
- Optional: under Settings, then Storage, turn on removing worktrees after merge.
  Without it, the worktree stays for you to remove.

## Choose models per role

Each role in `~/.tstack/models.md` names seats as `harness/model@effort`.
The `t3 instances` line maps each harness name to a T3 provider instance and its effort setting:

```text
t3 instances: claude=claudeAgent/effort, codex=codex/reasoningEffort, pi=pi/thinking, grok=grok/reasoningEffort
```

To use a second account, add a provider instance in T3, then give it its own harness name, such as `claude-work=claude-work/effort`, and use `claude-work/...` seats.
Rerun `$tstack-setup` to check every seat against what T3 offers.

## Where questions and decisions show up

The lead asks you in its own thread.
When a lead needs a decision, it writes the question to `.tstack/tasks/<task id>/decisions/` and asks you through the harness's question tool when it has one, otherwise in plain text.
It records your answer in the same file.

A lead that an autopilot's coordinator launched asks the coordinator instead, and the coordinator asks you.

A tool approval, such as a permission prompt in a lead or worker thread, appears in that thread's composer.
Approve it there.
A lead running with Full access rarely asks.

## Check on a lead

Open its thread, read along, and ask it where the task stands.
The lead treats anything you type in its thread as your instruction.
When you type into a worker's thread, that worker follows you and says so in its next report.

A lead that opens a pull request links it to its thread, so the PR's status shows beside the thread, and T3 settles the thread when the PR merges.
The PR watch has run live on T3, as the [first live task](../verification/2026-10-05-tstack-router-live-t3.md) records.
The linking has not yet run in a live task, and neither has reading T3's thread history.

## Stop running work

Stop the lead's turn in its thread, then tell it what to change.
The lead stops its workers and makes no commits, pushes or new workers until you tell it to go on.
To stop an autopilot, tell its coordinator, which holds every lead.
A hold has not yet run in a live task.

## After the merge

The lead leaves the thread for you to archive.
With `pr` delivery, the linked PR settles the thread when it merges.
T3 removes the worktree on merge only when you turned that setting on, and otherwise the worktree stays for you.
For follow-ups, the lead lists them in its final reply, and you open a new thread for any you want.
