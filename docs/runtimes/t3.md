# tstack on T3 Code

This guide shows how tstack maps onto T3 Code, and how to set T3 up and check on running work.
[runtime-t3.md](../../skills/tstack/references/runtime-t3.md) owns the exact calls the agents make.

## What runs where

| Role | In T3 | Checkout |
| --- | --- | --- |
| Main | The thread you open and pin, with Full access | The project folder |
| Lead | A thread main launches, titled `<task id> lead` | Its own worktree on branch `task/<task id>` |
| Worker | A child task of the lead, titled `<task id> <name>` | The lead's worktree |

A worker that must build or run competing code, such as an arena candidate, gets its own thread and worktree instead.

## Set up T3 once

- Sign in to each provider your models file uses, under Settings, then Providers.
  Setup reads the providers T3 can run and refuses a model it does not list.
- Give main's thread **Full access**.
  T3 lets only a full-access thread start another thread in its own worktree.
- Pin main's thread, so T3 never settles it while tasks run.
- Optional: under Settings, then Integrations, turn on browser access, and device access for a mobile app.
  Leads and workers then drive your app in T3's browser or simulator, and save screenshots and recordings as evidence.
  This surface has not yet run in a live task.
- Optional: under Settings, then Storage, turn on removing worktrees after merge.
  Main archives a lead's thread after the merge, and leaves the worktree to T3 or to you.

## Choose models per role

Each role in `~/.tstack/models.md` names seats as `harness/model@effort`.
The `t3 instances` line maps each harness name to a T3 provider instance and its effort setting:

```text
t3 instances: claude=claudeAgent/effort, codex=codex/reasoningEffort, pi=pi/thinking, grok=grok/reasoningEffort
```

To use a second account, add a provider instance in T3, then give it its own harness name, such as `claude-work=claude-work/effort`, and use `claude-work/...` seats.
Rerun `$tstack-setup` to check every seat against what T3 offers.

## Where questions and decisions show up

Only main talks to you.
When a lead needs a decision, it writes the question to `.tstack/tasks/<task id>/decisions/` and messages main, and main asks you in its thread.
Your answer goes back to the lead.

A tool approval, such as a permission prompt in a lead or worker thread, appears in that thread's composer.
Approve it there.
A lead running with Full access rarely asks.

## Check on a lead

Ask main, for example:

```text
where is the greet task?
```

Main reads the lead's thread and its task folder and tells you where it stands.
You can also open the lead's thread yourself, read along, and type into it.
The lead treats anything you type there as your instruction, and tells main in its next report.

A lead that opens a pull request links it to its thread, so the PR's status shows beside the thread, and T3 settles the thread when the PR merges.
The PR watch has run live on T3, as the [first live task](../verification/2026-10-05-tstack-router-live-t3.md) records.
The linking has not yet run in a live task, and neither has reading T3's thread history.

## Stop running work

Tell main to stop, for example "stop the greet task".
Main interrupts the lead's turn and sends it a hold.
The lead cancels its workers and makes no more commits or pushes until you tell main to release it.
A hold has not yet run in a live task.
