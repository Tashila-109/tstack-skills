### Autopilot-stack

**A coordinator runs this program; it is not a lead's playbook.** For "autopilot-stack", "autopilot, don't merge", "stack them, don't ship", and "build the stack, I'll land it". Run [Autopilot-full](autopilot-full.md), but merge nothing: the human reviews and lands every PR. At each check-in, re-read both playbooks, and this one wins where they differ.

1. **In place of Autopilot-full step 1, hold the human's gates with no grant.** Ask for no merge grant and record none. State-then-wait, so a request to state the plan is not a go. Record the queue in `<home>/autopilot-<name>.md`, with each item's parent when it builds on another item.
2. **Stack a PR only when it builds on another PR.** This is the one exception to Autopilot-full step 3. Launch that item's lead once its parent's PR is stack-ready, branching from the parent's task branch at its audited head, with its PR targeting that branch, as **Size and stacks** in [Opening a PR](opening-a-pr.md) says. Every other item runs in parallel off the default branch. Each brief reports stack-ready in place of merge-ready.
3. **In place of Autopilot-full step 5, stop at verified.** A PR is stack-ready when Autopilot-full step 4's audit is clean at its current head. Post the audit summary on the PR as a comment. Never merge, arm auto-merge, close or retarget a PR. Leads push only their own branches, because the coordinator owns each stack's shape and the human owns the landing.
4. **Absorb drift without rewriting history.** Until landing starts, when the default branch moves in a way that can affect a PR that targets it, as Landing's merge-result test in [Shipping](shipping.md#landing) says, bring it in with `gh pr update-branch <pr>`, then cascade down that PR's stack, bringing each parent into its child the same way. These are merges, never force-pushes. When a merge conflicts in a lead's files, that lead resolves it on its own branch. After each update, compare every affected PR's patch-id with its audited one as [Shipping](shipping.md#landing) does, and send any PR whose patch changed back through the audit. Re-run checks after every update, even when the patch-id is unchanged.
5. **Deliver, then keep your hands off.** Give the human each PR's URL with its audit summary, listing stacked PRs from root to tip. The human reviews and lands them, a stack bottom up, or asks the coordinator to land them under [Shipping](shipping.md). Once landing starts, nobody writes to a PR being landed except the updates Shipping's Landing makes, because a second writer breaks a landing in flight. A problem mid-landing goes to the human, and any fix waits for their go.

**Choosing between the autopilots.** Autopilot-full when the run may merge. Autopilot-stack when the human lands the PRs.
